Prometheus 架构走读：组件分工与 Server 内部设计 ​

Prometheus 是云原生计算基金会（CNCF）的项目，也是目前最常用的开源监控系统之一。本文先建立整体架构视角，再走进 Prometheus Server 内部，看 main 函数、配置装载、服务发现与抓取这几个核心组件如何组织在一起。适合正在选型监控系统、或者想读懂 Prometheus 源码主干（以 v2.3.1 为参照）的开发者。

监控系统在解决什么 ​

按观测位置，监控分两类：白盒监控了解系统内部运行状态，通过指标观察预判问题；黑盒监控（HTTP 探针、TCP 探针等）在故障发生时快速通知。落地的典型诉求包括：长期趋势分析（如磁盘增长率推算扩容时间点）、版本间与容量间的对照分析、告警、故障定位，以及可视化。

数据模型与 PromQL ​

Prometheus 采集的监控数据以指标（metric）形式保存在内置的时间序列数据库（TSDB）中。每个样本除指标名外还带一组标签，基于标签可以方便地做聚合、过滤、裁剪：

text
http_request_status{code='200', content_path='/api/path', environment='production'} => [value1@t1, value2@t2, ...]
1

查询语言 PromQL 实现对监控数据的查询与聚合，也被用于 Grafana 可视化和告警规则，支持求分布范围、预测未来值、过滤 TopN 等操作。

整体架构 ​

几个组件的分工：

  1. Prometheus Server 是核心，负责监控数据的获取、存储与查询；
  2. Exporter 把采集端点以 HTTP 服务形式暴露给 Server，分为直接采集（目标本身支持）与间接采集（用 Client Library 写采集程序）两类；
  3. PushGateway 面向无法被拉取的临时任务，相当于指标中转缓存；
  4. AlertManager 接收 Server 产生的告警，负责后续的分组、抑制与路由投递（机制详见下文告警篇，此处不展开）。

Server 内部走读 ​

main 函数：装配与协调 ​

main() 负责初始化并运行所有组件，把相互依赖的组件连接起来，大致做三件事：

  1. 解析命令行配置。Prometheus 区分两类配置：基于 flag 的配置用于那些不支持不停机更新的简单设置；配置文件（--config.file）里的设置则必须支持不重启整机的热重载。
  2. 实例化组件。服务发现、目标抓取、存储等运行组件被实例化，并通过信道、引用或上下文传递连接。
  3. 运行组件。Server 以 actor-like 模型运行所有组件，用 oklog/run 的 run.Group 协调各 actor 的启动与关闭；多个信道用于强制顺序约束，例如在存储就绪、初始配置加载完成之前不启用网络接口。

配置子系统 ​

配置子系统负责读取、校验、应用 yaml 配置文件。加载（或热重载）时调用 config.LoadFile() 把文件解析到 config.Config 顶层结构体，其成员反映配置文件的层次结构，每个成员有默认配置和 UnmarshalYAML() 方法，在解析的同时做有效性校验。

Reload handler 是 main 中实现的一个 goroutine，监听来自网络接口或 HUP 信号的重载请求；收到后重新 LoadFile()，并调用各支持热更新组件的 ApplyConfig() 把新配置应用下去。Termination handler 同理监听 TERM 信号，返回后经 run.Group 触发各组件有序关闭。

Scrape discovery manager：发现目标 ​

它是一个 discovery.Manager，通过服务发现机制查找并持续更新需要抓取的目标列表，独立于实际执行抓取的 scrape manager 运行，通过同步信道向后者提供目标组更新流。

每个配置里定义的服务发现机制实例各跑在自己的 goroutine 中：比如 scrape_config 定义了两个 kubernetes_sd_config，管理器就运行两个独立的发现实例。每个实例实现 Discoverer 接口，把目标更新发给 discovery manager，后者汇聚后转发给 scrape manager。配置变更时，管理器停掉当前所有发现实例，按新配置重启。

Scrape manager：执行抓取 ​

scrape manager 管理所有抓取对象：目标按 group 分组（每个 group 对应一个 job_name），每个 group 一个抓取池，池内对每个目标 endpoint 启动一个 ScrapLoop，按配置的间隔循环抓取。

收到某池的目标更新后，抓取池先为每个目标添加默认 label，再按 target relabeling 配置生成最终要抓取的目标列表。为了让同一 job 的多个目标在抓取间隔内均匀错开，每个目标根据其标签集与最终抓取 URL 计算哈希，用哈希值在区间内选一个确定的偏移量。ScrapLoop 周期性地发 HTTP 请求抓取目标，并按 Prometheus 的文本暴露格式解析样本写入存储。

小结 ​

  • Prometheus 的角色拼图：Server 拉取并存储、Exporter 暴露指标、PushGateway 兜底临时任务、AlertManager 管告警投递。
  • Server 内部围绕 run.Group 的 actor 协调组织：main 装配、Reload/Termination handler 处理信号、discovery manager 管目标发现、scrape manager 管抓取循环，两者以同步信道解耦。
  • flag 与配置文件的双轨配置设计，决定了哪些设置能热重载、哪些必须重启，二次开发或运维排障时值得先分清这一点。
