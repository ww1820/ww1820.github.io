clashctl mixin 覆写规则：让指定域名绕过代理直连 ​

在 Linux 服务器上以订阅方式使用 Clash/mihomo 时，经常遇到一类问题：某个域名本应直连（内网服务、特定工具的 API 端点），却被订阅规则送进了代理节点，导致访问变慢甚至不通。直接改订阅生成的配置文件当然可以，但下次订阅更新就会被整个覆盖。本文记录 clash-for-linux-install（提供 clashctl 命令的安装管理脚本）的 mixin 覆写机制：把指定域名的 DIRECT 规则持久地插到订阅规则前面，订阅更新后依然生效。适合在无桌面环境、用该脚本托管 mihomo 的读者。

clashctl 的配置布局 ​

先搞清楚文件在哪、谁是谁。clashctl 不是独立二进制，而是 bashrc 里 source 的 shell 函数：

bash
export CLASHCTL_HOME=/home/<user>/clashctl
. $CLASHCTL_HOME/scripts/cmd/clashctl.sh
1
2

所以非交互 SSH（ssh host 'clashctl status'）会报 command not found，需要先手动 export + source 再调用。

配置都在 $CLASHCTL_HOME/resources/ 下，mihomo 进程实际以 -d resources -f runtime.yaml 运行：

文件 作用
config.yaml 订阅原始配置，clashctl sub 更新时整个被覆盖
mixin.yaml 用户覆写配置，订阅更新后仍保留
runtime.yaml mixin 与 config 合并后的最终运行配置

为什么改 mixin 而不是直接改 config.yaml ​

Clash/mihomo 的 rules 是顺序匹配：想让指定域名绕过代理，必须把 DIRECT 规则插到订阅规则前面。直接编辑 config.yaml 虽然立刻生效，但下次订阅更新就被冲掉。mixin.yaml 是该项目官方的持久化覆写机制，合并逻辑在 scripts/lib/config.sh 里：

runtime.rules = mixin.rules.prepend + config.rules + mixin.rules.append
1

mixin 各字段的适用范围（mixin.yaml 文件头部注释有说明）：

字段 行为 适用
prepend 插到原列表开头 rules、proxies、proxy-groups
append 追加到原列表末尾 rules、proxies、proxy-groups
override 按 name 整体替换 proxies、proxy-groups
inject 向指定 proxy-group 注入节点 proxy-groups

一个容易踩的坑：项目 wiki 上写的字段是顶层 prepend-rules，但实际安装版本用的是嵌套结构 rules.prepend。字段写法以安装版本的合并脚本（scripts/lib/config.sh）为准，别照抄 wiki。

操作步骤 ​

编辑 resources/mixin.yaml，在 rules.prepend 列表加一条（改前先备份）。示例让 zcode.z.ai 及其子域直连：

bash
cd $CLASHCTL_HOME/resources
cp mixin.yaml mixin.yaml.bak
# 在 rules: -> prepend: 下追加一条，或用 sed 插到现有条目后
sed -i '/api64.ipify.org/a\    - DOMAIN-SUFFIX,zcode.z.ai,DIRECT' mixin.yaml

合并后的 rules 段长这样：

yaml
rules:
  prepend:
    - DOMAIN,api64.ipify.org,DIRECT
    - DOMAIN-SUFFIX,zcode.z.ai,DIRECT # 新增
  append:

生效走项目自己的合并重启路径，clashctl mixin -e 保存后自动触发；非交互场景直接调内部函数（效果等价）：

bash
export CLASHCTL_HOME=/home/<user>/clashctl
. $CLASHCTL_HOME/scripts/cmd/clashctl.sh
_merge_config_restart   # 合并校验，失败会回滚 runtime.yaml，成功则重启 mihomo
1
2
3

注意 _merge_config_restart 会重启 mihomo 进程，已建立的长连接（如流式 API 的 SSE 连接）会被掐断，客户端重连即走新规则。

验证：三步缺一不可 ​

1. 确认规则进了运行时配置且排在订阅规则前。 通过 mihomo 的外部控制 API 查规则顺序（secret 在 mixin.yaml / runtime.yaml 里）：

bash
curl -s -H "Authorization: Bearer <secret>" http://127.0.0.1:9090/rules \
  | python3 -c "import json,sys; [print(r['type'], r['payload'], '->', r['proxy']) for r in json.load(sys.stdin)['rules'][:3]]"
1
2

输出前几条应包含 DomainSuffix zcode.z.ai -> DIRECT。

2. 实际打一发流量，看日志命中。 查 rules 只能证明配置加载了，命中要看过连接日志：

bash
curl -x http://127.0.0.1:7890 -s -o /dev/null https://zcode.z.ai
grep "zcode.z.ai" $CLASHCTL_HOME/resources/mihomo.log | tail -2
1
2

日志出现 match DomainSuffix(zcode.z.ai) using DIRECT 才算真生效。

3. 确认本机直连本来就能通。 如果目标域名直连本身不可达，改成 DIRECT 反而把服务弄断了：

bash
curl --noproxy "*" -s -o /dev/null -w "%{http_code} %{time_total}s\n" https://zcode.z.ai
1

小结 ​

改代理规则优先找“覆写/override/mixin”这类机制，不直接动订阅生成的配置文件，否则更新即丢；字段写法以安装版本的合并脚本为准，wiki 文档可能落后于实际版本；生效验证不能只看配置加载，要打过真实流量看连接日志，并事先确认直连链路本身可达。规则粒度按需选：DOMAIN-SUFFIX,zcode.z.ai 只管该域及其子域，后续发现同主域其他子域也要直连时，可放宽为 DOMAIN-SUFFIX,z.ai。
