ROS2 消息序列化：从 .msg 到 CDR 字节流 ​

ROS2 的通信建立在 DDS 标准之上，一条消息从 publish() 到达对端，中间要经过代码生成、类型支持、CDR 编码三层机制。本文自顶向下拆解整条序列化管线：rosidl 如何把 .msg 变成 C++ 结构体，CDR 线格式如何对齐与编码，两种类型支持策略的差异在哪里，以及零拷贝 loaned message 的生效条件。适合写过 ROS2 节点、想理解消息传输开销来源或做中间件适配的读者。

rosidl 代码生成管线 ​

以 std_msgs/msg/String 为例，rosidl_generator_cpp 生成三类头文件（较新的发行版中后两类位于 msg/detail/ 子目录）：

文件 内容
string.hpp 顶层头文件，用户代码 include 这个
string__struct.hpp 消息 struct 定义，字段即成员变量
string__traits.hpp 编译时类型特性：is_message、has_fixed_size、has_bounded_size

生成的结构体是 plain struct，所有实现均在头文件中（header-only）。

ROS 类型到 DDS IDL 类型按固定映射转换：

ROS 类型 DDS IDL 类型 Wire 大小
bool boolean 1 字节
byte / uint8 octet 1 字节
float32 float 4 字节
float64 double 8 字节
int32 long 4 字节
int64 long long 8 字节
string string 变长
T[] sequence<T> 变长
T[N] T[N] 固定

CDR 线格式 ​

封装头 ​

每条 CDR 消息开头 4 字节，是 16 位 representation identifier（大端）加 16 位 options（通常为 0）：

text
字节 0-1: 编码格式标识 (representation id, 大端)
  0x00 = PLAIN_CDR Big Endian (XCDR1)
  0x01 = PLAIN_CDR Little Endian (XCDR1)    ← ROS2 默认
  0x02 = PL_CDR Big Endian (参数列表，发现数据用)
  0x03 = PL_CDR Little Endian
  0x08/0x09 = PLAIN_CDR2 Big/Little Endian (XCDR2, final 类型)
  0x0a/0x0b = DELIMITED_CDR2 Big/Little Endian (XCDR2, appendable 类型)
  0x10/0x11 = PL_CDR2 Big/Little Endian (XCDR2, mutable 类型)

字节 2-3: options 字段（通常为 0）

对齐规则 ​

每个基本类型按自然边界对齐，不足处补 padding：

cpp
struct Example {
    uint8  a;     // offset 0, 1 字节
                  // 3 字节 padding
    uint32 b;     // offset 4, 4 字节
    uint16 c;     // offset 8, 2 字节
                  // 6 字节 padding
    double d;     // offset 16, 8 字节
};                // 总计 24 字节

XCDR1 与 XCDR2 的关键差异在对齐上限：XCDR1 中 double、int64 等 64 位类型按 8 字节对齐，XCDR2 把所有基本类型的对齐上限收紧到 4 字节。这也是含 8 字节成员的 FINAL 类型在两种编码间不互通的原因——即使类型结构完全相同，padding 布局也不同。

复合类型编码 ​

String：[4 字节长度 N (uint32 LE)][N 字节 UTF-8 数据 + NUL 终止符]。长度包含结尾的 \0："hello" 编码为 06 00 00 00 68 65 6C 6C 6F 00（6 = 5 个字符加 1 个终止符）。

Sequence：[4 字节元素个数][元素1][元素2]...

Array：连续存储，无长度前缀。

Nested struct：递归应用 CDR 规则，从第一个字段的对齐要求开始。

两种类型支持策略 ​

ROS2 的 RMW 实现有两种获得序列化能力的方式，直接影响性能特征：

静态类型支持 ​

  • 编译时为每个消息类型生成专用序列化/反序列化函数
  • 每个 .msg 生成独立的函数实现，直接访问结构体成员
  • rmw_fastrtps_cpp 使用此方案
text
.msg → .idl → FastRTPS 代码生成器 → 专用的 serialize()/deserialize()
1

内省类型支持 ​

  • 编译时生成消息的元数据描述（成员名、类型、偏移量）
  • 运行时通过遍历元数据，用通用函数处理任意消息类型
  • rmw_cyclonedds_cpp 使用此方案；CycloneDDS 没有对应的每消息代码生成包，消息包无需为它重新编译

核心数据结构：

cpp
// 描述整个消息
struct MessageMembers {
    const char* message_namespace_;
    const char* message_name_;
    uint32_t member_count_;
    const MessageMember* members_;    // 字段描述数组
    size_t size_of_;                  // struct 的 sizeof
};

// 描述单个字段
struct MessageMember {
    const char* name_;
    uint32_t type_id_;
    size_t offset_;                   // 在 struct 中的偏移
    bool is_array_;
    uint32_t array_size_;
};

rmw_cyclonedds 的序列化实现细节 ​

两阶段序列化 ​

rmw_cyclonedds 把大小计算与数据写入分离：

  1. SizeCursor：遍历消息成员元数据，计算 CDR 编码后的总大小（不写数据）
  2. DataCursor：分配好 buffer 后，遍历成员写入实际数据

这样避免了动态 buffer 扩容。

Simple Type 快速路径 ​

对于 CDR 兼容内存布局的类型（所有成员是 primitive 且无对齐问题），直接 memcpy 跳过逐成员遍历：

text
首次序列化 → 检测消息是否 simple type → 缓存结果
后续序列化 → 命中缓存 → memcpy 整个消息体

零拷贝：Loaned Message ​

传统路径与零拷贝路径 ​

传统路径：用户消息 → memcpy → CDR 序列化 → DDS 发送，至少两次拷贝。

零拷贝路径：DDS 预分配 loaned buffer → 用户直接写入 → 共享内存传输。

关键 API ​

cpp
// 发布端借入
rmw_borrow_loaned_message(publisher, type_support, &loaned_msg);
// 写入数据后直接发布（发布后自动归还）
rmw_publish_loaned_message(publisher, loaned_msg, allocation);

// 订阅端借入
rmw_take_loaned_message(subscription, &loaned_msg, &taken, allocation);
// 用完释放
rmw_release_loaned_message(subscription, loaned_msg);

限制条件 ​

  • 仅支持固定大小类型（不含 string/sequence 等变长字段）
  • CycloneDDS 基于 iceoryx 实现，需 XML 启用 SharedMemory
  • QoS 限制（任一不满足则退回网络/拷贝路径）：Reliability = RELIABLE、Durability = VOLATILE、History = KEEP_LAST（深度不超过配置的池容量）、Liveliness = AUTOMATIC、Deadline = INFINITY
  • 环境变量 ROS_DISABLE_LOANED_MESSAGES=1 可全局禁用

固定大小检测 ​

通过 is_type_self_contained() 判断：

  • 不含 string/wstring（变长类型）
  • 不含无界 sequence
  • 所有嵌套子消息也必须 self-contained

要点 ​

  1. 序列化发生在 RMW 实现层，通过 TypeSupport 完成：静态方案每类型生成专用函数，内省方案运行时遍历元数据，二者在编译时间、二进制体积和运行时开销上互补
  2. 封装头解释了消息开头的 4 字节；XCDR1 与 XCDR2 的对齐上限差异（8 字节 vs 4 字节）意味着含 64 位成员的 FINAL 类型在两种编码间不互通
  3. 序列化的主要开销来自逐成员遍历、对齐 padding 计算和变长字段内存分配；纯 primitive 且布局兼容 CDR 的类型可走 memcpy 快速路径，真正跳过序列化只有零拷贝路径
  4. 零拷贝的条件是严格的：固定大小类型、iceoryx 共享内存、五项 QoS 全部满足；条件不满足时自动回退普通路径，功能不受影响
