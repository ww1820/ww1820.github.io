libhv 大响应被关闭：写缓冲上限与短写排查 ​

一个经 libhv 对外提供 HTTP 服务的接口，响应体约 20MB，客户端偶发收到 curl 错误 18（transfer closed with N bytes remaining to read）。本文记录一次完整排查：从量化复现、三方证据交叉定位，到控制变量实验解释"偶发"，最终落在 libhv 写缓冲的硬限制上。适合用 libhv（或任何带内部写缓冲的事件循环网络库）对外提供大响应接口的开发者。

建立反馈环：先量化"偶发" ​

用 curl 循环请求 20 次，结果 20/20 全部失败，且数据高度规整：

  • 每次都返回 HTTP 200（响应头正常发出）
  • 每次实际收到 110801 字节，完全相同
  • 每次剩余字节数也完全相同
  • 故障在约 0.23 秒内发生

截断点完全固定的特征，本身就排除了竞态假设——竞态必然带来字节数波动，而这里连一个字节的偏差都没有。

三方证据交叉定位 ​

strace 跟踪服务端 ​

对服务进程 strace，只抓一个请求，关键两行：

sendto(100, "HTTP/1.1 200 OK\r\nConnection: kee"..., 20971723, MSG_NOSIGNAL, NULL, 0) = 110960
close(100) = 0

2

服务端用单次 sendto 试图发出约 21MB 数据，内核只接受了 110960 字节——socket 发送缓冲已满，发生短写。紧接着进程主动 close(fd)。

libhv 自身日志 ​

通过 /proc/<PID>/fd 反查日志文件归属，libhv 自己写下了根因：

ERROR write bufsize > 16777216, close it! [nio.c:529:hio_write]
1

16777216 = 16MB，正是该版本 libhv 的 max_write_bufsize 上限。注意这个默认值随版本变化（libhv 新版 master 的 DEFAULT_MAX_WRITE_BUFSIZE 常量已改为 4MB），排查时以所用版本源码为准。

hio_write 标称线程安全，但"安全"仅指用递归互斥锁保护 write_queue 的入队操作。它不会在发送不下时阻塞等待，而是把未发送数据累计入队；一旦累计量超过 max_write_bufsize，直接判定为 ERR_OVER_LIMIT，异步关闭连接。

控制变量实验：解释"偶发" ​

对同一个 20MB 接口，只改变客户端的 SO_RCVBUF：

客户端 SO_RCVBUF 服务端 sendto 返回 libhv 行为 客户端结果
约 64KB（curl 默认） 110960（短写） 剩余超 16MB → close 失败，收到 110801 字节
64KB（python） 短写 同上 → close 失败，收到 2881824 字节
32MB（python） 20971718（全发） nwrite == len → done 成功，收到全部

客户端接收窗口大、抽取得快时，内核 send queue 始终有空位，send() 一次写完，不进 enqueue，自然不触发 16MB 判定。这同时证明了三件事：响应体本身没问题、网络链路没问题、故障完全由服务端 send() 短写量决定。

用户感知到的"偶发"由此解释：真实环境里客户端接收窗口、网络拥塞、并发请求对发送缓冲的争用都会影响短写量，偶尔短写后剩余不足上限就能侥幸成功。

被实验否决的假设 ​

假设 否决证据
跨线程写 socket 竞态 strace 显示单次 sendto，无竞态特征；截断点固定 110960
响应结束逻辑被调用两次导致状态跳转 libhv ERROR 产生于 hio_write 内部，早于任何结束逻辑
网络 MTU / 中间设备截断 32MB RCVBUF 能完整收到 20MB，排除链路问题
HTTP keepalive 复用旧连接 strace 显示是全新 accept

教训：在拥有可复现的反馈环之前，任何基于代码阅读的假设都站不住。本案例中，20 次 curl 的固定截断点在几分钟内就否决了"竞态"假设。

修复方向 ​

方案 改动量 评价
提高 max_write_bufsize 一行：writer->setMaxWriteBufsize(64MB) 或 hio_set_max_write_bufsize() 治标，单连接堆积大缓冲占内存，可立即止血
分块写响应体 改发送路径为分块多次写，配合写完成回调做背压 治本，需改业务代码
走 chunked / SSE 流式 复用已有流式路径 治本，适合大响应场景

修复后的回归验证三件套：curl 循环请求期望零失败；strace 确认 sendto 分批调用且无提前 close；libhv 日志不再出现 write bufsize 超限记录。

小结 ​

  • libhv 的 hio_write 非阻塞、不等待，发送不下时累计入队，超过 max_write_bufsize（上限值随版本不同）直接关连接——大响应加慢客户端是必现组合。
  • 固定截断点排除竞态、strace 抓短写与主动 close、库日志与源码对齐，是这类问题的高效定位路径。
  • 长期方案是分块写入加背压，或改用流式响应；调大上限只作临时止血。
