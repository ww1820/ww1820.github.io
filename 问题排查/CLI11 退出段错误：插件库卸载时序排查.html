CLI11 退出段错误：插件库卸载时序排查 ​

一个采用「CLI11 解析命令行 + 运行时加载插件注册子命令」架构的程序，功能一切正常，却在退出时发生段错误，调用栈指向 CLI::App 的析构函数。最终根因是插件管理对象先于 CLI 对象析构，dlclose() 把子命令析构代码所在的动态库卸载了。这类「析构顺序 × 动态库卸载」问题在插件化架构中相当典型，本文记录完整定位过程与通用解法，适合做插件化 CLI 或在退出路径崩溃的同学参考。

问题现象 ​

程序运行期间一切正常，退出时段错误。gdb 调用栈显示崩溃发生在 CLI::App 对象的析构过程中，且崩溃帧位于插件动态库（下文以 libcli-plugin.so 代指）内：

text
CLI::App::~App()                                       // 析构入口
std::vector<std::shared_ptr<CLI::App>>::~vector()      // 释放子命令列表
std::_Sp_counted_ptr_inplace<CLI::Option_group>::_M_dispose()
libcli-plugin.so!CLI::Option_group::~Option_group()    // 析构代码在插件 .so 中
    ← 段错误：此时插件库已被 dlclose 卸载，代码地址失效

栈有两个特征值得注意：

  • 崩溃点不在业务逻辑里，而在库对象的析构函数内；
  • 中间几帧属于插件动态库，说明崩溃时执行的是插件内实例化的代码。

根因分析 ​

CLI11 是一个流行的 C++ 命令行解析库，通常以单头文件（CLI11.hpp）形式集成。两个机制叠加导致了崩溃：

1. CLI::App 级联析构子命令。 CLI::App 内部以 std::vector<std::shared_ptr<CLI::App>>（源码中的 subcommands_）持有子命令，App 析构时逐个释放子命令对象。

2. 子命令的析构代码实例化在插件里。 CLI11 是 header-only 库，插件源文件包含 CLI11.hpp 后创建的子命令对象，其析构函数、shared_ptr 控制块的释放代码（_Sp_counted_ptr_inplace::_M_dispose()）等模板实例都编译在插件的 .so 中，不在主程序里。

于是当 PluginManager（负责加载/卸载插件的组件）先于 CLI::App 析构时：

dlclose() 卸载动态库后，库内代码不再映射在进程地址空间；CLI::App 随后析构子命令，跳转到已失效的地址，触发段错误。

解决方案 ​

核心原则一句话：任何依赖动态库中代码的对象（CLI 子命令、回调、shared_ptr 控制块等），必须在其所依赖的插件管理器之前完成析构。

对栈对象来说，就是控制声明顺序——先声明插件管理器，后声明 CLI 对象：

cpp
int main(int argc, char** argv) {
    PluginManager pm;   // 先声明 → 后析构（插件保持加载）
    CLI::App app;       // 后声明 → 先析构（此时插件仍可用）
    // ... 从插件注册子命令到 app ...
    try {
        app.parse(argc, argv);   // CLI11 标准用法：parse + exit
    } catch (const CLI::ParseError& e) {
        return app.exit(e);
    }
    return 0;
} // app 先析构 → pm 后析构 → 安全

反过来，用作用域块把插件管理器「提前收尾」是典型反例：

cpp
int main() {
    CLI::App app;
    {
        PluginManager pm;
        // 注册来自插件的子命令到 app
    } // 错误：pm 先析构，app 析构时插件已卸载
}

这个反例肉眼上很合理——「用完插件就释放」——但它把析构顺序问题藏进了作用域规则里。栈对象按声明逆序析构，作用域块内声明的对象又在块结束时先析构，两层规则叠加后 pm 必然先于 app 消亡。

延伸：插件化架构的一般约束 ​

这个问题并不限于 CLI11，它是「跨动态库边界的 C++ 对象」的通用约束：

  • 析构函数、虚函数、回调、shared_ptr 控制块的释放代码，都可能在创建该对象的 .so 里实例化；
  • 只要对象析构晚于所在 .so 的 dlclose，就是未定义行为；
  • 对全局/静态对象还要注意：不同编译单元之间静态对象的析构顺序标准未规定，依赖具体平台的链接器行为，比栈对象的逆序规则更不可控。

两条工程建议：

  1. 避免在插件中定义需要跨模块析构的非平凡类型，尤其是含虚函数或模板实例化的类；
  2. 把「注册进主程序的对象」的生命周期和插件句柄的管理显式绑定（如统一由 PluginManager 在卸载前清理），不要依赖偶然的声明顺序。

小结 ​

  • 退出时段错误、栈顶在库析构函数、中间帧在某个 .so：优先怀疑动态库卸载时序问题；
  • CLI11 的 App 以 shared_ptr 持有子命令，header-only 的特性使插件创建的子命令析构代码留在插件 .so 内；
  • 解法是保证插件管理器生命周期长于所有依赖插件代码的对象——栈对象靠声明顺序，静态对象不要跨模块析构；
  • dlclose 之后调用库内任何代码都是未定义行为，这类问题在虚函数、回调、智能指针控制块上都会以同样的方式爆发。
