Protobuf 动态加载报 File not found：DiskSourceTree 映射机制与修复 ​

在 C++ 程序里用 google::protobuf::compiler::Importer 在运行时动态加载 .proto 文件时，如果业务 proto 里写了 import "google/protobuf/descriptor.proto"（常见于自定义 Options 的场景），很容易撞上一串 File not found 错误。本文适合正在实现 proto 热加载、Schema 校验工具或通用网关插件的开发者，读完可以弄清报错根因、拿到可直接落地的修复写法，并了解如何在工程上预防这类问题。

现象 ​

动态加载业务 proto 文件时，Importer 报出如下错误：

text
[error] Error in 'google/protobuf/descriptor.proto' at -1:0: File not found.
[error] Error in 'biz.proto' at -1:0: Import "google/protobuf/descriptor.proto" was not found or had errors.
[error] Error in 'biz.proto' at 71:7: "google.protobuf.MessageOptions" is not defined.

2

复现条件很明确：业务 .proto 文件引用了 google/protobuf/ 下的标准文件（用于自定义 Options 或引用标准描述符），程序用 Importer 做运行时动态加载，而初始化 DiskSourceTree 时只映射了业务 proto 所在目录。

根因：DiskSourceTree 是一张显式映射表 ​

DiskSourceTree 是 Importer 解析 import 语句时使用的虚拟文件系统。它是一张完全显式的路径映射表，不继承任何环境变量，也没有系统默认搜索路径。这一点与 protoc 命令行工具不同——protoc 自带默认的 include 搜索逻辑，而 DiskSourceTree 里没映射的路径就是找不到。

当 proto 文件请求 google/protobuf/descriptor.proto 时，SourceTree 必须存在一条能把 google/protobuf 前缀解析到磁盘上真实物理目录的映射，否则直接返回失败。只调用 MapPath("", business_proto_dir) 把业务目录映射为根，标准库路径自然无从解析。

修复：把标准库目录也映射进来 ​

关键是理解 MapPath(virtual_path, disk_path) 的语义：把虚拟前缀 virtual_path 映射到磁盘目录 disk_path，import 路径去掉虚拟前缀后拼到磁盘目录后面。

推荐直接映射 include 根目录、保留完整相对路径：

cpp
google::protobuf::compiler::DiskSourceTree source_tree;

// 1. 映射业务 proto 目录
source_tree.MapPath("", protoDir.generic_string());

// 2. 映射 Protobuf 标准库所在的 include 根目录
//    import "google/protobuf/descriptor.proto" 会拼出
//    /usr/include/google/protobuf/descriptor.proto（正确）
source_tree.MapPath("", "/usr/include");

// 错误：去掉虚拟前缀 "google/protobuf" 后只剩 descriptor.proto，
// 会去找 /usr/include/descriptor.proto
source_tree.MapPath("google/protobuf", "/usr/include");

如果要用 google/protobuf 作虚拟前缀，磁盘路径必须对应到 .../include/google/protobuf 这一层。两种写法等价，选一种即可。

工程上不建议硬编码路径，可以在启动时探测常见候选目录，找到确实包含标准 proto 的那一个再映射：

cpp
std::vector<std::string> candidates = {
    "/usr/include", "/usr/local/include", "/opt/homebrew/include"};
bool mapped_std = false;

for (const auto& base_path : candidates) {
    std::filesystem::path check_file =
        std::filesystem::path(base_path) / "google" / "protobuf" / "descriptor.proto";
    if (std::filesystem::exists(check_file)) {
        source_tree.MapPath("", base_path);
        mapped_std = true;
        break;
    }
}
if (!mapped_std) {
    throw std::runtime_error("Standard protobuf include directory not found.");
}

预防策略 ​

三个层面的建议：

  1. 封装初始化逻辑。不在业务代码里直接实例化 DiskSourceTree 并手动 MapPath，而是封装统一的加载器类，在构造时完成标准库路径的探测与映射。
  2. 路径由构建系统注入。标准库路径不应写死在源码里，通过 CMake/Bazel 取得 PROTOBUF_INCLUDE_DIR，用宏定义或配置文件传入运行时。
  3. 加载后做健康检查。Importer 创建完成后立即导入一个最小的标准文件（如 google/protobuf/empty.proto），失败就抛出明确异常，把问题暴露在初始化阶段，而不是等加载业务文件时才报出令人困惑的 File not found。

小结 ​

  • Importer + DiskSourceTree 动态加载时，标准库 import 找不到，根因是 DiskSourceTree 只认显式映射、没有默认搜索路径。
  • 修复是把 protobuf 标准库所在的 include 根目录也映射进来；映射时留意 MapPath 虚拟前缀与磁盘目录的对应层级。
  • 工程化做法是封装初始化、路径注入、加载健康检查三件套，把这类错误挡在启动阶段。
