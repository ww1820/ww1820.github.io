spdlog 分类日志混入专属文件排查：FilterSink 按名过滤方案 ​

多个分类共用一个分发 sink 时，运行期追加的文件 sink 会收到所有分类的日志——本文分析这个混入问题在 spdlog 里的产生机制，并给出一个不改动分发结构、在写入处按日志名过滤的包装 sink 方案。适合在自封装日志库里使用 spdlog、需要「某些分类额外落到专属文件」的开发者。读完可以弄清 dist_sink 的分发语义、拿到一份可直接移植的 FilterSink 实现，以及配套的验证方法。

问题现象 ​

一个基于 spdlog 封装的日志库按「分类」组织日志：每条日志属于 user、func、net、exception 之类的分类，分类名同时是 spdlog 的 logger 名。进程里有两类落盘需求：

  • 一个默认文件（如 app.log），收全部或大部分分类；
  • 一个异常专属文件（如 exception.log），只收 exception 分类。

现象是：exception.log 建好之后，user、func、net 的日志也源源不断写进来，专属文件变成第二个全量日志。

机制：dist_sink 分发时不看日志来自谁 ​

这个日志库的分发结构与 spdlog 原生用法不同。早期为了解决一次并发问题（旧实现持锁改写各 logger 的 sinks_ 列表，与写日志线程存在数据竞争），所有 logger 被改为只挂一个共享的 dist_sink，运行期新增输出端时向这个分发 sink 追加 sink。

dist_sink 的分发逻辑（spdlog v1.5.0，spdlog/sinks/dist_sink.h:58-67）：

cpp
void sink_it_(const details::log_msg &msg) override
{
    for (auto &sink : sinks_)
    {
        if (sink->should_log(msg.level))
        {
            sink->log(msg);
        }
    }
}

它把同一条消息转给下面挂的每个 sink，转发前只判断等级（should_log，非虚函数，spdlog/sinks/sink.h:23），不看消息来自哪个 logger。rotating_file_sink 收到就写。

于是混入的时序是：

  1. 进程启动，创建默认文件 sink，挂到 dist_sink；
  2. 业务运行，user、func、net 等 logger 陆续创建，都只挂这个 dist_sink；
  3. 初始化走到异常模块，创建 exception.log 的文件 sink，也挂到 dist_sink；
  4. 此后所有分类的日志都会被分发到这个新 sink——它成了全量文件。

关键点：挂载顺序不影响结果，第 3 步无论发生在第 2 步之前还是之后，exception.log 都会收到全部分类。这不是竞态，是 dist_sink 的设计语义。

也不能回到「每个 logger 自己维护 sinks 列表」的原生做法来修——那正是当年数据竞争的来源：改写 sinks_ 的线程和写日志的线程操作同一个容器，锁不覆盖。

方案：在写入处包一层按名过滤的 FilterSink ​

分发结构不动，全部分类继续共用一个 dist_sink。变化只在文件 sink 这一层：带名单的文件外面套一层 FilterSink，写入前核对消息的 logger 名，不在名单里的不写；不带名单的文件、网络 sink、终端 sink 不过滤。

cpp
class FilterSink : public spdlog::sinks::base_sink<spdlog::details::null_mutex>
{
public:
    FilterSink(sink_ptr inner, std::unordered_set<std::string> allow)
        : _inner(std::move(inner)), _allow(std::move(allow))
    {
        if (_inner)
        {
            // 沿用内层文件 sink 的等级，供 dist_sink 按等级过滤
            set_level(_inner->level());
        }
    }

protected:
    void sink_it_(const spdlog::details::log_msg &msg) override
    {
        if (!_inner || msg.logger_name.data() == nullptr || msg.logger_name.size() == 0)
        {
            return;
        }

        // 核对日志分类名，确认该日志能否写入当前文件
        const std::string name(msg.logger_name.data(), msg.logger_name.size());
        if (_allow.find(name) == _allow.end())
        {
            return;
        }
        _inner->log(msg);
    }

    void flush_() override
    {
        if (_inner)
        {
            _inner->flush();
        }
    }

    void set_formatter_(std::unique_ptr<spdlog::formatter> sink_formatter) override
    {
        if (_inner && sink_formatter)
        {
            _inner->set_formatter(sink_formatter->clone());
        }
        formatter_ = std::move(sink_formatter);
    }

private:
    sink_ptr _inner;                         // 真正写文件的 sink
    std::unordered_set<std::string> _allow;  // 允许写入的分类名
};

一条日志的走向：

各输出的实际收日志范围：

输出 收哪些分类 等级
app.log 全部，含 exception debug 以上
err_app.log 全部 warn 以上
exception.log 只有 exception debug 以上
err_exception.log 只有 exception warn 以上
网络、终端 全部 全收

归属规则是叠加的：exception 的日志同时进 app.log 和 exception.log。专属文件是「额外」而不是「独占」，如果业务上要独占，把默认文件的收流范围反过来设计即可。

分类名从哪里来 ​

过滤依据是消息里的 logger 名，这个机制完全在 spdlog 侧，与封装层无关：

  • spdlog::logger 构造时传入的名字存在 name_ 成员里（spdlog/logger.h:348）；
  • 每次写日志，spdlog 把 name_ 填进消息的 logger_name 字段（spdlog/logger.h:154，类型是 string_view_t，定义在 spdlog/details/log_msg.h:18）；
  • dist_sink 转发消息时原样携带这个字段，FilterSink 里用 msg.logger_name 就能取到。

所以「分类」只需要在创建 logger 时作为名字传入，之后每条日志天然带着它，不需要额外传参。

为什么不用 spdlog 原生的做法 ​

spdlog 里让某个分类写指定文件的原生做法，是给 logger 单独配 sink：

cpp
auto exception_logger = spdlog::rotating_logger_mt("exception", "exception.log", ...);
1

logger 和文件一对一，logger->log() 直接走自己的 sink，不存在混入。

但这要求「logger 创建时就知道自己的全部输出端」。本文的场景是运行期动态挂输出端、且全进程共享一个分发 sink 的库——logger 创建时专属文件可能还不存在，两者在时间上解耦。原生做法里「哪个 logger 对应哪个文件」这层关系不存在，FilterSink 补的就是这一层：绑定关系放在各个 FilterSink 自己的名单里，构造时一次写定，没有全局登记表。

顺带说明：spdlog 1.5.0 自带的 sink 里没有按 logger 名过滤的（sinks/ 目录下 msg.logger_name 只被当作日志内容使用，如 systemd_sink.h:64 写进 SYSLOG_IDENTIFIER、dup_filter_sink.h:67 透传），这个包装层需要自己实现。

设计要点 ​

用到的 spdlog 扩展点是 base_sink<Mutex>。它把 log、flush、set_pattern、set_formatter 四个公开方法定成 final（spdlog/sinks/base_sink.h:26-29），加锁后转调子类重写的 sink_it_、flush_ 等虚函数（:36-39）。FilterSink 重写了 sink_it_、flush_、set_formatter_ 三个。几个决策的理由：

  1. 过滤放在写入处，没有创建顺序要求。logger 先建、专属文件后建，或者反过来，结果相同。另一条思路是按分类分组、每组一个 dist_sink，但那要求专属文件先于名单里的分类创建，顺序耦合更紧，所以没有采用。
  2. 没有绑定表。名单在构造 FilterSink 时一次写定，之后只读。运行期会变的共享状态只剩 dist_sink 的 sink 列表，由它自己的锁保护。
  3. 包装层用 null_mutex。写日志线程走 dist_sink::sink_it_，建文件线程走 dist_sink::add_sink（dist_sink.h:34-38），两处拿的是同一把锁；FilterSink 的 log、flush、set_formatter 都由 dist_sink 持锁后调用（dist_sink.h:58-67、:69-88），外层已经串行化，包装层再加锁是重复开销。
  4. 等级靠构造时拷贝。dist_sink 分发前调的 should_log 是非虚函数，判的是包装层的等级。FilterSink 构造时把内层等级拷过来，挂载时先 set_level 再包装，err 文件就不会收进 info 行。代价是这是一次性拷贝——之后单独改内层 sink 的等级，包装层不会跟着变，扩展时要连着一起改。
  5. 格式要转发。set_formatter_ 把格式对象克隆一份交给内层，否则全局改格式改不到专属文件。
  6. 新增接口而不是给旧接口加默认参数。CreateFileSink("a", {"b"}) 和 CreateFileSink("a", {"b", "c"}) 同名重载在 g++ 9 下报 ambiguous，所以带名单的版本单独命名。

行为约束 ​

移植这个方案时需要知道的边界行为：

  • 名单为空或只有空串：不建文件，也不报错；
  • 名单内的分类同时仍写默认文件（叠加语义，见上文表格）；
  • 专属文件建好之前的日志留在默认文件，不会事后搬过去；
  • 同名重复调用会得到两个写同一文件的 sink，接口层没有去重。

怎么验证 ​

这个改动的验证分四层，方法可以复用到类似的 sink 扩展上。

编译：改动文件用 g++ 9.4.0 直接编译，-Wall -Wextra -pedantic 零告警。

功能矩阵：按真实调用顺序写一个验证程序，对比四种组合下各文件的行数与分类构成：

场景 app.log exception.log err_app.log err_exception.log
新库 + 配套调用 7 行，全部分类 2 行，只有 exception 3 行 1 行，只有 exception
新库 + 旧调用（不加名单） 7 行 7 行，全部分类 3 行 3 行
新库，专属文件先于默认文件创建 同第一行 同第一行 同第一行 同第一行
旧库 + 旧调用 7 行 7 行，全部分类 3 行 3 行

第二行值得注意：只换库、不改调用方式，混入现象不变——过滤逻辑在调用侧的名单里，库和调用要成对更新。

线程安全（TSan）：光跑正常路径的 TSan 是不够的，需要阳性对照来确认检测器在工作：

对象 条件 结果
计数器阳性对照 两线程各 100 万次自增同一变量 报 1 处
注入竞争的副本 另起线程无锁改写 FilterSink 的名单成员 报 20 处，落在 unordered_set 的查找与插入
未改动的实现 4 个写线程，运行期挂 600 个文件 sink，建完后再写 3 秒，共 116,730 条 0 处，退出码 0

ABI 兼容：对比新旧动态库的符号表——只增不删，新增的是过滤接口的符号。旧头文件编译的调用方加载新库正常；新头文件编译的调用方加载旧库，启动即报 undefined symbol（x86_64 工具链默认 BIND_NOW）。结论是升级方向安全、降级方向不兼容，发布时库和头文件要成对。

结论 ​

  • 分类日志混入专属文件，根源是 dist_sink 只按等级分发、不看 logger 名——挂上去的每个 sink 都收全量，与挂载顺序无关；
  • 在「全部 logger 共享一个分发 sink」的结构里，按名过滤放在写入处最稳：FilterSink 包装文件 sink，核对 msg.logger_name 后再转发，绑定关系构造时写定，无全局登记表；
  • 实现上注意四个细节：等级从内层拷贝、formatter 转发给内层、包装层用 null_mutex（依赖外层 dist_sink 的锁）、新接口单独命名避免重载歧义；
  • 验证要覆盖功能矩阵、带阳性对照的 TSan、以及符号表层面的 ABI 检查。
