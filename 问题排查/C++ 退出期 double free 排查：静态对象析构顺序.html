C++ 退出期 double free 排查：静态对象析构顺序 ​

程序运行期间一切正常，退出时却崩在 double free or corruption。这类崩溃往往不是堆管理写错，而是静态对象的析构顺序问题：两个全局对象，一个的析构函数访问另一个，而被访问的可能早已销毁。本文记录一次完整的排查过程——从堆栈定位根因，到为什么直觉修法「改成单例」在这种形态下并不奏效，以及两种可靠的修法与验证手段。

现象 ​

进程收到退出信号、事件循环正常结束之后，abort 崩溃：

bash
[info] loop exit.
double free or corruption (fasttop)
[1] 442962 abort (core dumped)  ./demo_app

崩溃点不在任何业务代码的调用栈里，而是在程序终止阶段。

从堆栈定位根因 ​

backtrace 的底部不是 main，而是 __cxa_finalize 与 _dl_fini——说明崩溃发生在静态对象析构阶段。关键堆栈帧：

text
#28 __cxa_finalize           # 程序终止，开始析构全局对象
#27 ~unordered_map           # 析构静态注册表 service_registry
#20 ~pair                    # 析构表中的元素
#14 ~ServiceImpl             # 元素是服务实现对象
#12 releaseMonSocket         # 服务析构时释放自己的监控 socket
#11 map::erase               # 从另一个静态表 mon_sockets 里 erase
#4  _int_free                # double free 检测触发

service_registry 是一个静态的 unordered_map，登记所有服务实现对象；mon_sockets 是另一个静态表，按名字持有各服务的 ZeroMQ 监控 socket。服务对象析构时要从 mon_sockets 里 erase 自己的 socket——两个静态对象之间在析构期存在依赖。

根因：析构顺序没有保证 ​

C++ 标准对静态存储期对象销毁顺序的规定是：

  • 同一编译单元内，按构造的逆序析构；
  • 跨编译单元，构造顺序未指定，因此析构顺序也未指定。

service_registry 与 mon_sockets 定义在不同的编译单元里。退出时如果 mon_sockets 先被析构，service_registry 析构链上的 map::erase 就是在操作一个已析构的 std::map——内部结构早已释放，再次释放触发 glibc 的 double free 检测。

静态对象的构造顺序受链接顺序、对象文件排列等细节影响，同样的代码在不同编译器或不同链接配置下可能一次正常、一次崩溃，这类问题的排查成本远高于在构造阶段规避。具体机制可参考 cppreference：Static Initialization Order Fiasco。

为什么「改成单例」修不好 ​

看到「静态对象析构顺序不可控」，一个常见的直觉修法是把被依赖的对象改成函数局部静态的单例（Meyers Singleton），期望「第一次使用时才构造」能顺带解决析构问题：

cpp
class MonSocketHolder {
public:
    static std::map<std::string, std::shared_ptr<zmq::socket_t>>& getInstance() {
        static std::map<std::string, std::shared_ptr<zmq::socket_t>> instance;
        return instance;
    }
};

这个修法解决的是初始化顺序：局部静态变量在首次使用时构造，一定晚于依赖它的代码；C++11 起标准还保证并发初始化只执行一次（magic statics）。

但它不解决析构顺序。析构同样按构造逆序执行：service_registry 在 main 之前构造，单例要到运行期首次使用时才构造，退出时单例先析构——~service_registry 再走 getInstance() 时，拿到的已经是被析构过的对象，问题依旧。isocpp FAQ 对此有明确说明：把 construct-on-first-use 写成局部静态对象，"仍然正确处理初始化问题，但不再处理逆初始化问题"，若其他静态对象的析构函数在它析构后再使用它，程序就会崩溃。

单例写法只在一种情形下恰好安全：依赖的首次使用（也就是它的构造）早于所有使用者的构造——依赖先构造、后析构，使用者析构期间依赖仍然存活。本例不满足这一条件：注册表在程序启动期构造，socket 表要到运行期首次使用时才构造，依赖反而先析构。这也印证了处理静态对象生命周期的一条基本原则：析构函数不做跨对象访问，问题才真正消失。系统讨论四种单例生命周期方案（shared_ptr 托管、指针版手动 destroy、Phoenix 复活、消除依赖），见 C++ 单例析构顺序：静态销毁时序与四种应对。

修法一：有意不析构 ​

被依赖的静态对象改用指针持有，永远不 delete，退出时交给操作系统回收：

cpp
class MonSocketHolder {
private:
    static std::map<std::string, std::shared_ptr<zmq::socket_t>>* mon_sockets;

public:
    static std::map<std::string, std::shared_ptr<zmq::socket_t>>& getMonSockets() {
        if (!mon_sockets) {
            mon_sockets = new std::map<std::string, std::shared_ptr<zmq::socket_t>>();
        }
        return *mon_sockets;
    }
};
// 不提供 delete：对象不参与退出期析构，「被先析构」的可能性被整个消除

new 出的对象不在静态析构清单里，~service_registry 无论何时运行，mon_sockets 都存活。isocpp FAQ 给出的安全写法正是这种泄漏式指针。

代价：静态分析工具与内存检查器会报告泄漏；退出时必须正确清理的资源（落盘、断开连接）不适用。对于「进程退出即一切作废」的监控表类资源，这是最简单可靠的方案。

修法二：atexit 显式清理 ​

在静态析构阶段开始前，先手动清空依赖链的源头：

cpp
void cleanup() {
    service_registry.clear();  // 显式清空，元素析构时 mon_sockets 仍存活
}

int main() {
    std::atexit(cleanup);
    // ...
}

标准保证 atexit 注册的函数与静态对象析构按注册逆序交错执行：main 里注册的 cleanup 早于所有启动期构造的静态对象析构。service_registry 被提前清空后，真正的 ~service_registry 无事可做，不会再触碰 mon_sockets。

代价：清理顺序要手工维护，注册点容易遗漏。适合退出路径清晰、依赖源头少（一两个注册表）的程序。

两个容易误判的变体 ​

  • 静态 shared_ptr 成员：把静态对象包进静态的 shared_ptr 并不能改变它的析构时机——静态成员本身仍是静态对象，退出期照常析构。要让生命周期由使用方决定，应当由使用方持有 shared_ptr 拷贝，即姊妹篇中的 shared_ptr 托管方案。
  • 跨动态库的静态对象：除编译单元间的顺序问题外，动态库的卸载顺序还受依赖关系与 dlclose 时机影响，静态对象的析构可能发生在库卸载时而非进程退出时，问题形态更多一层。

验证方法 ​

bash
# Valgrind 检测内存问题（invalid read / double free 的定位）
valgrind --leak-check=full --track-origins=yes ./demo_app

# AddressSanitizer 编译，崩溃点直接指向首次非法访问
g++ -fsanitize=address -g demo_app.cpp

# gdb 观察两个静态对象的析构先后顺序
gdb ./demo_app
(gdb) rbreak ~        # 对所有析构函数设断点，观察触发顺序
(gdb) run

要点 ​

  • 退出期 double free or corruption 且栈底是 __cxa_finalize，优先怀疑静态对象析构顺序问题
  • 跨编译单元静态对象的析构顺序未指定；析构函数访问其他静态对象是未定义行为的常见来源
  • Meyers 单例只保证初始化顺序，不保证析构顺序；依赖在运行期才首次使用时，单例反而先析构
  • 「析构期还要被别的静态对象访问」的资源，用有意不析构（泄漏式指针）或 atexit 提前清理；能消除析构依赖就消除
  • 修复后用 Valgrind / AddressSanitizer 验证，用 gdb 析构断点确认顺序
